## 0. Goal

Build an Android and iOS mobile app of the existing **C-Core-Bloom** JAMB CBT practice platform that:

- Is a **near-exact replica** of the web app (same screens, flows, branding, behaviour).
- Supports **both roles**: **User** (JAMB candidate) and **Admin**, using the existing role logic.
- Stays **in sync** with the web app: same Supabase backend, same business logic, and web updates flow into the mobile build automatically.
- Works on **all phone sizes** (small phones, large phones, tablets, foldables) in portrait and landscape.
- Is **optimized by device capability** (processor cores, RAM, storage, network), because many users are on low-end Android phones with limited, expensive data.
- **Does not modify the web app in any way.**

Known stack of the web app (verify by reading `package.json`, do not assume): React 19, TypeScript, Vite, shadcn/ui, Tailwind, Supabase (Auth, Postgres with RLS, Edge Functions).

## 2. Recommended Architecture: Capacitor wrapper that consumes the web source

### Why Capacitor (and not React Native/Expo rewrite)

The web app uses React + shadcn/ui + Tailwind. A React Native rewrite would force rebuilding every screen, so it could not stay a close replica and would drift from the web app. **Capacitor** runs the same React code inside a native WebView with access to native plugins, so the mobile app is a true replica and stays in sync.

Confirm this choice in Phase 0. If you find a blocker, report it and propose an alternative before writing code.

### How "not touching the web app" works

The `mobile/` folder has its **own** `package.json`, `vite.config.ts`, and entry point. Its Vite config **aliases the web `src` folder** so the mobile build compiles the real web code without modifying it.

```
c-core-bloom/
├── src/                      <- WEB APP (read-only for us)
├── supabase/                 <- BACKEND (read-only for us)
├── package.json              <- WEB (read-only)
└── mobile/                   <- EVERYTHING NEW GOES HERE
    ├── package.json
    ├── vite.config.ts        <- aliases "@" to ../src
    ├── tsconfig.json
    ├── capacitor.config.ts
    ├── index.html            <- mobile entry HTML (viewport-fit=cover, etc.)
    ├── src/
    │   ├── main.tsx          <- mobile entry; mounts the web <App />
    │   ├── native/           <- Capacitor-only code (status bar, back button, deep links, storage)
    │   ├── overrides/        <- mobile versions of specific web modules (see below)
    │   ├── perf/             <- device-tier detection and optimizations
    │   └── styles/mobile.css <- safe-area and touch-size fixes only
    ├── android/              <- generated by Capacitor
    ├── ios/                  <- generated by Capacitor
    ├── scripts/              <- sync, web-safety-check, build helpers
    ├── MOBILE_NOTES.md
    └── WEB_CHANGE_REQUESTS.md
```

### The override pattern (how mobile differs without editing web files)

When a web module cannot work as-is on mobile (for example it uses `window.localStorage` in a way that is unsafe, uses `window.open`, or assumes a mouse), **do not edit it**. Instead:

1. Create a replacement in `mobile/src/overrides/` with the **same exports**.
2. Add a Vite alias or small resolver plugin in `mobile/vite.config.ts` that swaps the web module for the override **only in the mobile build**.
3. Log every override in `mobile/MOBILE_NOTES.md` with the reason, so I can review them.

Keep overrides **as few and as thin as possible**. Wrap the web module rather than reimplementing it where you can.

### Phase 5: Performance and optimization by device processor and RAM

Create `mobile/src/perf/deviceProfile.ts` that classifies the device **once at startup** and exposes a `DeviceTier`.

#### 5.1 Detect capability

Use whatever is available, with safe fallbacks because not all APIs exist on every platform:

| Signal | Source | Notes |
|---|---|---|
| CPU cores | `navigator.hardwareConcurrency` | Available in Android WebView and iOS WebView |
| RAM | `navigator.deviceMemory` (Android WebView, coarse values like 0.5, 1, 2, 4, 8) | **Not available on iOS**. Fall back to model or OS-based tiering |
| Device info | `@capacitor/device`: `getInfo()` (model, OS version, `memUsed`, `realDiskFree`, `webViewVersion`) | Use for model/OS and storage |
| Network | `@capacitor/network` | Detect `cellular` vs `wifi` and offline. Also `navigator.connection.saveData` and `effectiveType` where available |
| Battery | `@capacitor/device` `getBatteryInfo()` | Reduce work on low battery |
| Reduced motion | `prefers-reduced-motion` | Always respect |
| Frame performance | Measure average frame time during first 2 seconds of animation | Optional runtime refinement: if frames are slow, downgrade the tier |

#### 5.2 Tier definitions (starting values, tune with real measurements)

| Tier | Typical devices | Rule of thumb |
|---|---|---|
| **LOW** | RAM <= 2 GB **or** cores <= 4 **or** Android <= 9 **or** saveData on | Budget phones, old phones |
| **MID** | RAM 3-4 GB and cores 6-8 | Common mid-range |
| **HIGH** | RAM >= 6 GB and cores >= 8 | Flagships and recent iPhones |

If RAM is unknown (iOS or old WebView), derive tier from cores and OS/model, and **default to MID, never HIGH**.

#### 5.3 What each tier changes

Implement these through a single `useDeviceTier()` hook and CSS classes on `<html>` (`tier-low`, `tier-mid`, `tier-high`). Apply them **from `mobile/`** (CSS and overrides), never by editing web components.

| Area | LOW | MID | HIGH |
|---|---|---|---|
| Animations/transitions | Off or very short (no blur, no large shadows, no backdrop-filter) | Short, transform/opacity only | Full |
| List rendering | Virtualize all long lists, page size 10-20, render window small | Virtualize lists over about 50 items, page 25 | Page 50, larger window |
| Images | Smallest sizes, lazy-load, WebP/AVIF, no autoplay, aggressive decoding limits | Responsive sizes, lazy-load | Normal quality |
| Prefetch | None. Fetch only what the screen needs | Next-screen prefetch on Wi-Fi only | Prefetch on Wi-Fi |
| Cache size | Small and capped (for example 50-100 MB), evict LRU | Medium | Larger |
| Concurrent requests | 2 | 4 | 6 |
| Realtime channels | Minimal, unsubscribe off-screen | Normal | Normal |
| Heavy components (charts, rich editors, PDF/DOCX tools) | Lazy-load on demand, simplified or paginated versions where possible | Lazy-load | Lazy-load |
| JS memory | Release large objects on screen exit, avoid keeping all subjects' questions in memory at once | Moderate | Relaxed |
| Debounce/throttle | Longer (search and scroll handlers about 300 ms) | about 200 ms | about 100 ms |

Because the web app has a **PostgREST 1000-row cap** history, keep using the web's existing pagination logic for question fetching. Do not remove it. Fetch by subject, cache per subject, and never load all 15 subjects' questions at once on LOW-tier devices.

#### 5.4 Build-level optimization (inside `mobile/`)

- [ ] Vite production build with minification, tree-shaking, code-splitting per route (use `React.lazy` through mobile-side wrappers or `manualChunks` in `mobile/vite.config.ts`), and `build.target` matching the minimum Android WebView (Chrome 90+ or the actual minimum from `minSdk`).
- [ ] Track bundle size. **Set a budget** (for example initial JS under 300 KB gzipped, and report anything bigger) and add a `rollup-plugin-visualizer` report script.
- [ ] Compress and convert assets at build time (WebP/AVIF, subset fonts, `font-display: swap`). Bundle fonts locally rather than loading from Google Fonts at runtime.
- [ ] Android: `minSdkVersion` 24 (or as decided), R8/ProGuard shrinking and resource shrinking on release, **ABI splits** or AAB so users download only their CPU architecture (`arm64-v8a`, `armeabi-v7a`), and enable the AAB format for Play Store. Keep the APK/AAB as small as possible, since data is expensive.
- [ ] Ensure hardware acceleration is on, and avoid layout thrash (batch DOM reads/writes), `will-change` only where measured.
- [ ] Avoid long JS tasks (over 50 ms). Move heavy parsing (PDF/DOCX/MCQ import, large JSON) out of the main thread or keep it admin-only and lazy.
- [ ] Debounce Supabase calls, batch writes (exam answers), and use `select` with only needed columns.
- [ ] Enable HTTP compression and caching headers awareness: rely on Supabase's defaults but verify with the network panel.

#### 5.5 Verify optimization (required evidence)

Report numbers for **LOW, MID, HIGH** emulator or real-device profiles:

- Cold start time to login screen.
- Time to first question in an exam.
- JS heap after 10 minutes of an exam session, and after navigating through all main screens (watch for leaks).
- Dropped-frame rate while scrolling the longest list and switching exam questions.
- Total data used for: login, loading a subject, finishing a 40-question exam, opening the admin dashboard.
- APK/AAB download size per ABI.

## 4. Web Safety Check (run before every commit)

Create `mobile/scripts/web-safety-check.sh` (or `.ts`) that fails if any file outside `mobile/` changed:

```bash
#!/usr/bin/env bash
# Fails if anything outside mobile/ was modified, added, or deleted vs the base branch.
BASE="${1:-main}"
CHANGED=$(git diff --name-only "$BASE"...HEAD; git diff --name-only; git ls-files --others --exclude-standard)
OUTSIDE=$(echo "$CHANGED" | grep -v '^mobile/' | grep -v '^$' || true)
if [ -n "$OUTSIDE" ]; then
  echo "BLOCKED: files outside mobile/ were changed:"
  echo "$OUTSIDE"
  exit 1
fi
echo "OK: web app untouched."
```

Also add a CI job that runs this on every PR from `feat/mobile-app`.
